Sept défauts dans un projet que j'avais déjà rendu

J'ai rouvert un projet noté et livré. En trois jours de relecture, j'ai trouvé sept défauts — dont trois qui rendaient le système faux.

Projet : Gestion des stocks et des commandes — microservices Spring Boot

Sommaire — 6 sections
  1. Défaut n° 1 : la passerelle répondait 404 sur toutes les routes
  2. Défaut n° 2 : deux commandes simultanées vendaient le même article
  3. Défaut n° 3 : une quantité négative augmentait le stock
  4. Ce que ces trois défauts ont en commun
  5. La question que je pose maintenant à chaque fonctionnalité
  6. Ce qu'on peut en retirer

Le projet était rendu. Noté. Rangé.

Quatre services Spring Boot — découverte, passerelle, produits, commandes — un docker-compose.yml qui démarre, une démonstration qui passe. J'avais coché la grille d'évaluation ligne à ligne.

Six mois plus tard, j'ai voulu le remettre dans mon portfolio. Avant de le montrer, j'ai relu le code comme si quelqu'un d'autre l'avait écrit. Trois jours plus tard, j'avais sept défauts. Trois d'entre eux ne dégradaient pas le système : ils le rendaient faux.

Voici les trois, et ce que leur découverte a changé dans ma façon de relire.

Défaut n° 1 : la passerelle répondait 404 sur toutes les routes

Le plus embarrassant, parce que le plus visible — et que personne ne l'avait vu, moi comprise.

L'architecture prévoyait que tout passe par la passerelle : le client appelle localhost:8080/api/produits, Spring Cloud Gateway consulte Eureka, trouve le service produits, et transmet. Pendant la démonstration, j'avais appelé les services directement sur leurs ports, parce que c'était ce que j'avais sous la main dans Postman. La passerelle démarrait. Elle apparaissait dans Eureka. Elle était verte.

Elle ne routait rien.

La cause tenait en une ligne de configuration :

spring:
  cloud:
    gateway:
      discovery:
        locator:
          enabled: false

enabled: false. La valeur par défaut. Je n'avais jamais écrit true, et rien ne me l'avait signalé — une passerelle sans route n'est pas une passerelle en erreur, c'est une passerelle vide. Elle démarre parfaitement.

Ce que j'en retiens : un composant qui démarre n'est pas un composant qui fonctionne. « Vert dans Eureka » répond à la question « est-ce que le processus tourne », pas à la question « est-ce qu'il fait son travail ». Ce sont deux questions distinctes, et je n'en avais posé qu'une.

Le dépôt contient maintenant un script qui appelle chaque route via la passerelle et compare le résultat à un appel direct. Il tourne dans la CI. Si la passerelle redevient vide, la fusion est bloquée.

Défaut n° 2 : deux commandes simultanées vendaient le même article

Celui-là ne se voit pas en cliquant. Il faut le chercher.

Le service commandes réservait le stock en trois temps :

Produit p = produitClient.getProduit(id);   // 1. lire
if (p.getQuantite() < demande) {            // 2. vérifier
    throw new StockInsuffisantException();
}
produitClient.decrementer(id, demande);     // 3. écrire

Lire, vérifier, écrire. Trois appels réseau séparés, et rien entre eux.

Avec un seul client, ce code est juste. Avec deux clients simultanés sur le dernier article en stock, les deux lisent quantite = 1, les deux passent la vérification, les deux décrémentent. Le stock tombe à -1, et deux personnes ont acheté le même objet.

Je ne l'ai pas trouvé en lisant. Je l'ai trouvé en écrivant un test qui lance deux commandes en parallèle sur un stock de 1 :

@Test
void deuxCommandesSimultanees_uneSeuleDoitReussir() throws Exception {
    creerProduit("P1", 1);
    var pool = Executors.newFixedThreadPool(2);
    var barriere = new CyclicBarrier(2);

    List<Future<Boolean>> resultats = List.of(
        pool.submit(() -> { barriere.await(); return commander("P1", 1); }),
        pool.submit(() -> { barriere.await(); return commander("P1", 1); })
    );

    long reussies = resultats.stream().filter(this::sansErreur).count();
    assertEquals(1, reussies);      // avant correctif : 2
    assertEquals(0, stockDe("P1")); // avant correctif : -1
}

La CyclicBarrier est la partie importante. Sans elle, les deux tâches démarrent à quelques millisecondes d'écart et la première a le temps de finir : le test passe, et il ne prouve rien. La barrière les fait partir au même instant. C'est ce qui rend le défaut reproductible au lieu d'intermittent.

Le correctif n'a pas été de mettre un verrou dans le service commandes — il aurait protégé une instance et une seule. Il a été de déplacer la décision là où se trouve la donnée : le service produits décrémente désormais de façon conditionnelle, en une seule requête.

UPDATE produit
   SET quantite = quantite - :demande
 WHERE id = :id
   AND quantite >= :demande

Zéro ligne modifiée signifie stock insuffisant. La base tranche, une seule fois, et le résultat ne dépend plus de l'ordre d'arrivée.

Ce que j'en retiens : dès qu'une décision porte sur une donnée partagée, la séquence lire-vérifier-écrire est fausse par construction. Elle n'est pas « risquée sous forte charge » : elle est fausse. Deux requêtes suffisent à le démontrer.

Défaut n° 3 : une quantité négative augmentait le stock

Celui-ci m'a coûté le plus en amour-propre, parce qu'il est trivial.

Commander -5 articles appelait decrementer(id, -5), qui exécutait quantite = quantite - (-5). Le stock montait. Le total de la commande, lui, devenait négatif.

Il n'y avait aucune validation sur la quantité entrante. Aucune. J'avais annoté mes DTO avec @NotNull et je m'étais arrêtée là, en confondant deux questions : « le champ est-il présent ? » et « la valeur a-t-elle un sens ? »

public record LigneCommande(
    @NotNull String produitId,
    @NotNull @Min(1) Integer quantite   // @Min(1) : ajouté après coup
) {}

Une annotation. Le correctif fait un caractère de plus que le défaut.

Ce que j'en retiens : la validation d'entrée n'est pas une politesse défensive, c'est une règle métier écrite à l'endroit où elle se vérifie. « Une quantité commandée est un entier strictement positif » est une phrase du domaine autant que « une commande appartient à un client ». Je traitais la première comme de la plomberie et la seconde comme du métier. C'est la même chose.

Ce que ces trois défauts ont en commun

En les alignant, un motif est apparu — et c'est ça, le vrai enseignement.

DéfautCe que je testaisCe que je ne testais pas
Passerelle videLe service démarreLe service remplit son rôle
Vente doubleUn utilisateur à la foisDeux utilisateurs au même instant
Quantité négativeLes valeurs plausiblesLes valeurs hostiles

Trois fois la même erreur : j'avais testé le cas que j'avais en tête en écrivant le code. Or c'est exactement le cas qui ne peut rien révéler. Le code et le test sortaient de la même hypothèse ; ils ne pouvaient que s'accorder.

Un test n'a de valeur que s'il vient d'ailleurs que du code qu'il vérifie.

La question que je pose maintenant à chaque fonctionnalité

J'ai gardé trois questions de cette relecture. Elles tiennent en une ligne chacune et elles ont trouvé des défauts dans tous les projets où je les ai posées depuis.

  1. Si ce composant tombait en panne silencieusement, est-ce que je le verrais ? Si la seule preuve de bon fonctionnement est « ça démarre », la réponse est non.
  2. Que se passe-t-il si deux personnes font ça au même instant ? Pas « en forte charge ». Deux personnes. Un test à deux fils suffit à répondre.
  3. Quelle est la valeur la plus hostile que ce champ accepte ? Zéro, négatif, vide, très grand, la chaîne vide. Une par une.

Aucune ne demande d'outil. Elles demandent de se placer ailleurs qu'à l'endroit d'où on a écrit le code.

Ce qu'on peut en retirer

Un projet rendu et noté n'est pas un projet vérifié. La note évalue ce qui a été montré ; la relecture évalue ce qui a été écrit. Ce ne sont pas les mêmes objets.

Ce que je referais dans cet ordre :

  • Relire à froid, plusieurs mois après, en se donnant le rôle d'une personne extérieure. Trois jours ont suffi pour sept défauts.
  • Écrire le test avant le correctif, et vérifier qu'il échoue. Un test qui n'a jamais échoué ne prouve rien — il documente une intention, pas un comportement.
  • Faire de la démonstration une commande, pas une séquence de clics. Ce qui n'est pas scripté n'est pas reproductible, et ce qui n'est pas reproductible finit par ne plus être vrai sans que personne ne le remarque.

Les sept défauts sont documentés un par un dans le dépôt, chacun avec le script qui le démontre et le correctif qui le ferme. Les quatre que je n'ai pas racontés ici sont plus ennuyeux — mais ils sont là aussi, parce qu'un post-mortem qui ne garde que les défauts intéressants n'est plus un post-mortem.
