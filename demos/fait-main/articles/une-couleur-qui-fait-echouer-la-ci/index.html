Une couleur qui fait échouer l'intégration continue

J'ai mis mes couleurs sous contrôle automatique. Le script a refusé ma palette dès le premier jour — et il avait raison sur un point que je n'avais pas vu.

Le contraste d'une couleur n'est pas une opinion. C'est un quotient.

ratio = (L_claire + 0,05) / (L_sombre + 0,05)

Où L est la luminance relative, calculée à partir des trois composantes de la couleur avec une correction gamma. Quinze lignes de code. Le résultat va de 1:1 (deux couleurs identiques) à 21:1 (noir sur blanc).

La norme WCAG 2.1 fixe les seuils : 4,5:1 pour du texte courant, 3:1 pour du texte large et pour les éléments d'interface porteurs de sens — bordures de champs, icônes fonctionnelles.

Tout cela est connu. Ce qui l'est moins, c'est ce qui arrive quand on branche ce calcul dans une intégration continue et qu'on lui donne le droit de refuser une fusion.

Le script qui bloque

Le principe tient en une décision : le vérificateur ne produit pas un avertissement, il sort avec un code d'erreur.

const echecs = paires.filter((p) => p.ratio < p.min);
process.exit(echecs.length ? 1 : 0);

Trois lignes. C'est tout ce qui sépare un rapport qu'on lit quand on y pense d'une règle qui s'applique.

# .github/workflows/verification.yml
- name: Contraste des couleurs
  run: node outils/check-contrast.js

À partir de là, une couleur non conforme ne peut plus entrer dans la branche principale. Pas « ne devrait plus ». Ne peut plus.

Premier jour, premier refus

J'ai lancé le script sur ma palette initiale, plutôt fière de l'avoir choisie avec soin.

FAIL    1.58:1  min 3    border / bg    Bordure de champ (critère 1.4.11)

1,58:1 pour un seuil à 3. J'utilisais #C3CEE3 — un bleu-gris très pâle — pour toutes les bordures du système. Sur mon écran, le résultat était élégant : des cadres discrets, une interface qui respire.

Sur un écran moins bon, dans une pièce éclairée, ou pour quelqu'un dont la vision des contrastes est réduite, ces cadres n'existent pas. Or un champ de formulaire dont on ne distingue pas la bordure n'est pas discret : il est invisible. On ne sait plus où cliquer, ni combien de champs il y a.

Ma première réaction a été mauvaise. J'ai pensé : *le seuil est trop sévère pour un simple filet.*

Le seuil n'était pas le problème — ma catégorie l'était

En relisant le critère 1.4.11, j'ai vu ce que j'avais raté. Il ne s'applique pas à « toutes les bordures ». Il s'applique aux éléments porteurs d'information : ceux qui indiquent où se trouve un composant, quel est son état, quelle est sa limite.

Un filet purement décoratif — un séparateur entre deux paragraphes, une ligne sous un titre — n'informe de rien. Il n'est soumis à aucun seuil.

J'avais un seul token border pour deux intentions différentes. La norme ne me demandait pas d'assombrir tous mes filets. Elle me demandait de savoir lesquels disent quelque chose.

La correction n'a donc pas été de baisser le seuil, ni d'assombrir toute l'interface. Elle a été de couper le token en deux :

"border":      { "value": "#8C8275", "usage": "Bordures porteuses de sens — champs, séparateurs d'articles" },
"border-soft": { "value": "#E3DCD0", "usage": "Filets purement décoratifs (hors exigence 1.4.11)" }

border passe à 3,59:1 : on voit où sont les champs. border-soft reste pâle : les séparations décoratives ne crient pas.

Le résultat visuel est meilleur qu'avant. Avant, tout avait la même importance, donc rien n'en avait. Maintenant la hiérarchie est visible : ce qui délimite un objet manipulable se distingue de ce qui aère une page.

La contrainte n'a pas appauvri la palette. Elle m'a obligée à nommer une distinction que je faisais déjà sans le savoir — et un système de design, c'est exactement ça : des distinctions nommées.

Le champ usage, qui fait tout le travail

Chaque couleur du fichier porte un texte qui décrit son rôle, jamais sa teinte :

"accent": { "value": "#A63D26", "usage": "Liens, filets de section, étiquettes de rubrique" }

C'est une petite discipline, avec deux effets disproportionnés.

D'abord, elle rend le thème sombre possible sans réécriture. accent vaut #A63D26 en clair et #E8845F en sombre. Si le token s'appelait terracotta, la valeur sombre serait un mensonge — ce n'est plus la même couleur. Comme il s'appelle accent, les deux valeurs sont deux réponses correctes à la même question.

Ensuite, elle rend les revues possibles. « Est-ce que ce gris est bien ? » n'a pas de réponse. « Est-ce que ce gris convient pour une date de publication ? » en a une, et le script la donne.

Une source, tout le reste généré

Le fichier tokens.json est la seule chose qu'on modifie à la main. Trois artefacts en sont dérivés :

02-design/tokens.json
  ├── assets/style.css        généré · variables CSS, thèmes clair et sombre
  ├── rapport-contraste.md    généré · le tableau de conformité
  └── visuels sociaux         générés · aux mêmes couleurs, par construction

L'intérêt n'est pas d'économiser des frappes. C'est qu'il devient impossible de diverger. Le cas que ce montage empêche est précis : quelqu'un ajuste une couleur directement dans le CSS, parce que c'est plus rapide, et le rapport de contraste continue d'afficher l'ancienne valeur. Le rapport n'est pas faux — il est périmé, ce qui est pire, parce qu'il inspire toujours confiance.

Une source unique et un script qui bloque suppriment cette possibilité, au lieu de demander à chacun d'y penser.

Le bilan actuel

✔ 32 paires testées, toutes conformes.

Seize paires par thème, deux thèmes. Ratio moyen sur les paires de texte : 8,45:1, pour un seuil AA à 4,5:1. Onze paires sur seize atteignent AAA.

Ces chiffres ne sont pas un objectif que je me serais fixé. Ce sont les valeurs qu'a produites une palette conçue sous contrainte — et c'est le point de tout l'article.

Ce qu'on peut en retirer

Une règle qu'on peut ignorer n'est pas une règle. Le même calcul de contraste, dans un document de recommandations, aurait été respecté quelques semaines puis oublié à la première urgence. Branché sur une CI avec un code de sortie, il tient tout seul.

Et quand une vérification automatique refuse votre travail, le premier réflexe — assouplir le seuil — est presque toujours le mauvais. La question utile est : qu'est-ce que ce seuil sait de mon système que je n'ai pas encore formulé ?

Ici, il savait que j'avais deux sortes de bordures. Je ne le savais pas.
