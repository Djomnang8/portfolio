Ce qui démarre et ce qui marche

Bonjour,

Premier envoi de cette lettre. Le principe : tous les quinze jours, l'article publié la veille, plus une chose apprise en le fabriquant qui n'est pas dedans. Si ça ne vous convient pas, le lien de désinscription est en bas et il fonctionne du premier coup.

L'article

Sept défauts dans un projet que j'avais déjà rendu

J'ai rouvert un projet noté et livré six mois plus tôt. Trois jours de relecture, sept défauts, dont trois qui rendaient le système faux : une passerelle qui renvoyait 404 sur toutes les routes, deux commandes simultanées qui vendaient le même article, et une quantité négative qui augmentait le stock.

Les trois avaient la même cause de fond : j'avais testé le cas que j'avais en tête en écrivant le code.

Ce qui n'est pas dans l'article

Le test de concurrence m'a pris quatre heures, et trois heures et demie l'ont été pour une raison stupide : mon premier test passait toujours, avant et après le correctif.

Je lançais deux appels dans deux fils d'exécution, et je m'attendais à voir la vente double. Rien. Le test était vert sur le code défectueux.

La cause : les deux fils ne partaient pas au même instant. Entre le moment où le premier submit() est traité et le second, il s'écoule quelques millisecondes — largement de quoi laisser la première transaction se terminer. Je testais donc deux commandes successives, très rapprochées. Ce qui fonctionne parfaitement.

La correction tient en un objet :

var barriere = new CyclicBarrier(2);
// dans chaque tâche, avant l'appel :
barriere.await();

Chaque fil attend que l'autre soit arrivé. Ils repartent ensemble. Le défaut apparaît à tous les coups.

Ce que j'en garde dépasse la concurrence : un test qui passe avant le correctif ne teste pas ce qu'on croit. Je fais maintenant systématiquement l'inverse — j'écris le test, je le lance sur le code non corrigé, et je vérifie qu'il échoue. S'il passe, ce n'est pas le code qui est bon. C'est le test qui est faux.

Ça paraît évident écrit comme ça. Je l'ai appris en perdant une demi-journée.

Une chose lue

La documentation de Spring Cloud Gateway indique discovery.locator.enabled avec sa valeur par défaut, false, dans un tableau de la page de référence. Je l'avais lue. J'avais lu la ligne sans lire la valeur — on parcourt un tableau de configuration en cherchant le nom de l'option, et on ne regarde pas la colonne d'à côté.

Depuis, quand je copie une configuration depuis une documentation, je copie aussi la colonne des valeurs par défaut dans un commentaire. C'est laid. Ça m'a déjà évité une deuxième occurrence.

À dans quinze jours,

Joyce
